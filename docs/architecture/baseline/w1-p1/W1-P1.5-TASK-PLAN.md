## 1. Objective

Characterize, through the **public surface only**, the **acknowledged (asynchronous) data-loading contract** of `EnhancedSelect`: the `dataLoading.protocol='acknowledged'` request/completion/projection protocol, the public `startDataLoading` / `completeDataRequest` / `getDataLoadingState` API, and the public async events (`search`, `loadMore`, `error`, `diagnostic`, `dataRequestCancel`, `dataProjection`, `dataLoadingConfigError`).

### 1.1 The core thesis (why these contracts are not yet `Existing`)

Every P1.5-targeted contract currently carries **private-seam-only** coverage. The existing suites that touch this surface drive it through `as any` private access:

- `phase-2e-acknowledged-data-loading.spec.ts` — titled "**private** acknowledged EnhancedSelect integration"; uses `_enableAcknowledgedDataLoadingForTest`, `_completeDataRequestForTest`, `_loadMoreItems`, `_state`, `_dataRequestCoordinator`.
- `phase-2f-public-facade.spec.ts` — titled "public" but still uses `(select as any)._handleSearch`, `_loadMoreItems`, `_failNextAcknowledgedProjectionForTest`.
- `data-loading/request-coordinator.spec.ts`, `data-loading/public-config.spec.ts`, `data-loading/min-search-characters.spec.ts` — validate the coordinator/config in isolation (DOM-independent), not the component's public facade.
- `public-config-integration.spec.ts` — per-instance `dataLoading` config rejection/dedup (partly public).

This increment **converts** those private/peripheral findings into **public-surface black-box characterization**. That is the wiring-completeness question for the async protocol: does the public API/event/config surface expose the acknowledged protocol's behavior without reaching into internals?

### 1.2 What this increment does NOT do

- No production source change.
- No change to any accepted behavioral test (incl. `phase-2e-*`, `phase-2f-*`, `data-loading/*`, `public-config-integration`).
- No upgrade of the **five deferred P1.4 residuals** (EVENT-009, CONFIG-001, CONFIG-003, CONFIG-004, CONFIG-026) — see §8.
- No remediation of the **P1.4 gaps** (PART-009, ATTR-023, CONFIG-023) — see §2.3.
- No ADR, no removal/implementation of `pageLoaded`, no cross-browser parity work.

## 7. Pre-identified risks & classification risks

1. **EVENT-005 `pageLoaded` is declared-only (Missing).** Plan: T2 proves **negative** (pagination completion does not emit `pageLoaded`) and records *which* channel signals completion (`loadMore` / acknowledged `dataProjection`). Likely remains **`Missing`** or is **reclassified** as a documented DEVIATION-02 gap — **not** silently upgraded. Needs Lead decision at closure on the class (`Missing` vs a deviation-tracked disposition).
2. **Private-seam dependency risk.** `phase-2f` "public facade" still uses `_handleSearch`/`_failNextAcknowledgedProjectionForTest`. P1.5 must reproduce the same behaviors through *genuinely public* driving (config + public methods + `[part="input"]`). If a behavior is **only** reachable via a private seam (e.g. injected projection failure `_failNextAcknowledgedProjectionForTest`), it is recorded as a **public-unobservable gap**, not forced — analogous to ATTR-023.
3. **Async determinism.** Acknowledged protocol is inherently asynchronous (`startDataLoading` deferred hold, projection task). All assertions must synchronize on `getDataLoadingState()` / `expect.poll` / awaited public promises; no fixed sleeps. Any flake is a test defect, not a pass-retry.
4. **Non-data-loading invalid config (API-032) scope.** `updateConfig` invalid emission covers both `dataLoading` validation errors (`dataLoadingConfigError`) and the broader invalid-config surface; must bound exactly which emission is asserted and avoid over-claiming.
5. **`resource-limit` completion (API-062).** Cursor resource limits (`cursor-depth`/`cursor-token-size`) require cursor `paginationMode`; assert the `resource-limit` result and `getDataLoadingState().resourceLimit` without leaning on coordinator internals.
6. **LIFECYCLE-005 (Missing → likely Existing) subtlety.** The stale guard is observable *behavior* (stale result ignored), but proving "a guard exists" vs "the result happened to be benign" requires a scenario where a non-guarded implementation would visibly mutate. Must construct that discriminator publicly.
